1. Purpose of this document

This document sets out the three things: access to NEXT3, the infrastructure and messaging accounts, and AXA’s internal security review. It lists every open question arising from the BRD, and states the expected running cost of the application once live.

2. What is required, at a glance

  • A NEXT3 sandbox environment: URL, credentials, authentication method and test data
  • A decision on network connectivity to NEXT3
  • The choice of SMS provider for login codes, and an account in AXA’s name
  • Azure subscription access
  • The master list of experts, garages and claim officers from NEXT3 (ID, name, mobile number), if that data already exists there
  • Answers to the questions in sections 3.2, 3.3, 4 and 5

3. NEXT3 integration

3.1 The endpoints the application needs

Set out here so that the NEXT3 side can be scoped precisely. The paths shown are illustrative — what matters is the operation and the data, not the naming. Eight operations, plus a sandbox, cover the whole of the BRD.

EndpointWhat the application needs it for
Authentication
POST /auth/token		The application identifies itself to NEXT3 as a service. Whatever method NEXT3 already supports is fine — OAuth client credentials, an API key, or mutual TLS.
Claim details
GET /claims/{visaNumber}		Everything the expert sees on arriving at the scene: visa number, policy number, plate number, insured name and phone, car make and model, city, accident date.
Claim search
GET /claims/search		Search by plate number or visa number, for the expert’s “search previous claims” function and the claim officer’s visa lookup. The result must be limited to what that user is entitled to see — see Q5.
Claims assigned to an expert
GET /experts/{id}/claims		The list of claims currently assigned to one expert, so the application can show an expert their own work and refuse everything else. Also the fallback if NEXT3 cannot send an assignment notification.
Record arrival
POST /claims/{visaNumber}/arrival		Writes the “Expert Arrived” date, time and GPS location back to the claim.
Upload a document or photograph
POST /claims/{visaNumber}/documents		The core of the whole application. The file itself, plus its document type, the target folder (Expert documents or Survey), and a reference identifier supplied by the application so that a retry cannot create a duplicate (see Q3).
Master data — all user types
GET /experts
GET /garages
GET /claim-officers		Identifier, name, mobile number and active status for every user type that exists in NEXT3, not experts alone — garages and claim officers carry a NEXT3 identity in the BRD too. Needed so each app user can be matched to their NEXT3 record. If brokers also exist in NEXT3, an equivalent list is needed for them; otherwise the IRIS code list can come separately.
Assignment notification
a call from NEXT3 to the application		Tells the application that a visa has been assigned to an expert, so the expert’s phone can alert them. If NEXT3 cannot call outwards, the application will poll instead — see Q4.
A sandbox of all of the aboveA non-production environment with representative test data, so the integration can be built and tested without touching live claims.

3.2 Access and connectivity

These two shape the sequence of the entire build.

#QuestionWhat it decides
Q1On what date can a NEXT3 sandbox be made available — URL, credentials, authentication method (OAuth, API key or mutual TLS), rate limits and representative test data?The date development stops being able to run on a simulator.
Q2Is the integration a web API, or a shared directory for files plus record inserts into the NEXT3 database? The BRD prerequisites refer to identifying the directory to upload photos and insert records, which suggests the second. If it is the second: which database platform does NEXT3 use.These are two materially different builds. Confirming early avoids rework.

3.3 Further NEXT3 questions — required before week 3

Development can start without these, but each one is needed before the feature it concerns can be finished, and all of them before the real integration is wired in.

#QuestionWhy it matters
Q3Does NEXT3 recognise a reference identifier supplied by the calling application, and reject or ignore a repeat submission carrying the same one?Data integrity. If a connection drops after NEXT3 has accepted a photograph but before it confirms, the application must retry. Without a reference that NEXT3 checks against, that retry creates a duplicate photograph in the claim file.
Q4How does the application learn that a new visa has been assigned to an expert? The BRD states that a back-office engine triggers the process, but not how that reaches the application. A notification sent from NEXT3 to the application is strongly preferred; otherwise the application must poll NEXT3 on a schedule.The expert flow begins with a notification on the expert’s phone, so this must be resolved for the primary flow to work at all.
Q5How does NEXT3 express which expert is assigned to which claim? The application must be able to show an expert only their own assigned claims, and must refuse a request for anyone else’s. The same applies to the claim search: an expert searching by plate number must not be able to retrieve a claim that was never assigned to them. Which field or relationship carries that linkage, and is it returned by the claim endpoints?This decides whether the application can enforce access control at all. Without the assignment linkage from NEXT3, any logged-in expert could reach any claim in the system. It cannot be solved on our side, because the linkage lives in NEXT3.
Q6For the Expert Arrived update: which fields are written, by which endpoint, and in what date, time and coordinate formats?Named explicitly in the BRD; cannot be implemented on assumption.
Q7The master-data extract — for experts, garages and claim officers, not experts alone. In what format, and is it supplied once or kept synchronised? If brokers also hold a NEXT3 identity, please include them; otherwise we need the source of the IRIS code list.Required for onboarding, and so that every app user can be matched to their NEXT3 record. The BRD mentions only the expert extract, but all four profiles carry a NEXT3 identifier.
Q8Does NEXT3 accept audio files, and under which document type?The BRD requires the expert to record a voice note. If NEXT3 cannot store audio, an alternative needs agreeing.
Q9What are NEXT3’s rules for photographs? Maximum number per claim and per folder, maximum file size, accepted formats and any resolution limits. Separately: does AXA expect the application to perform any tampering or fraud checks on submitted images?The size and count limits shape the upload pipeline and are cheap to honour if known early. Fraud or tampering detection is a specialist capability and is not currently included — if AXA requires it, it needs to be scoped and quoted separately.
Q10Is there an AXA-standard car damage diagram or set of damage codes, or is free-form marking acceptable?Affects whether the damage-marking screen must match an existing AXA convention.
Q11When a claim officer finds that a visa does not yet exist, is it created directly in NEXT3 by the officer, or must the application create it?The BRD implies the officer leaves the app and retries. Confirmation avoids building an unnecessary function.

4. Running cost of the application

4.1 Assumed volumes

The BRD does not state volumes, so the figures below assume approximately 100 claims per day (about 3,000 per month), 15 photographs per claim at around 1.5 MB each, and approximately 200 users across all four profiles. Cost scales with these numbers, so please correct them if they are wrong — they are the single largest influence on everything in this section.

4.2 Hosting and platform

Assumes deployment to Microsoft Azure.

Storage is deliberately small, and it stays small. Photographs are held only until NEXT3 confirms receipt, then removed — NEXT3 remains the system of record, exactly as it is today.

4.3 Environments — a decision required from AXA

Does AXA want one environment or two? A single production environment is the cheaper option. Two — a test environment alongside production — means fixes and changes can be demonstrated and approved without touching live claim data, which AXA will almost certainly want once the application is in daily use. Two environments roughly doubles the figures in 4.2, and pairs naturally with a NEXT3 sandbox alongside NEXT3 production. My recommendation is two.

4.4 SMS for login — a decision required from AXA

Users log in with their mobile number and a one-time code sent by SMS, as described in the BRD. This requires a messaging account. I have deliberately not quoted a figure, because the per-message rate varies by provider and by country to a degree that any estimate would be misleading — Lebanon in particular is priced very differently across providers.

4.5 Mobile distribution

Required only if the application is published through the public app stores. Both accounts should be held in AXA’s name, as they carry the AXA identity under which the application is published.

5. Application behaviour — three decisions that change scope and timeline

These are not NEXT3 questions. Each one concerns how the application behaves, and each affects how long it takes to build. The intended approach is stated for all three — what is needed is confirmation, or an instruction to change it.

#QuestionEffect on scope and timeline
Q12Mobile and PC — the same features, or different? The BRD asks for an application installed on mobile or logged in PC. My assumption is one application, one login, used on either, with one unavoidable difference: the BRD requires car photographs to be captured, never uploaded from a file, and a desktop PC has no usable camera. So the capture steps are inherently a phone activity. Expert and Garage are field roles and will work on a phone; Claim Officer and Broker are desk roles and will mostly work in a browser. Is that split acceptable, or does AXA expect full feature parity on both?The assumption above costs nothing — it is one codebase. Full parity would mean allowing car photographs to be uploaded from a PC, which directly contradicts the capture-only rule in the BRD. That needs resolving before it is built, not after.
Q13Offline capture is not included in this phase. The application needs a data connection at the point of submission. Please confirm whether offline capture is a requirement.Not in the BRD and not in the current plan or price. If it is a requirement it is approximately one additional week and needs to be quoted — and it is materially cheaper designed in now than retrofitted later.
Q14The clarity check — this is the approach; please confirm it satisfies the requirement. The BRD requires that image visibility and voice clarity must be ensured. The application checks each photograph on the device as it is taken — resolution and sharpness — and immediately warns and offers a retake if it is too small, too dark or blurred. Voice notes are confirmed by playback before sending. This is a practical technical check: it does not judge whether the right subject was photographed.This is the approach allowed for in the estimate. Two things are not included and would each need separate scoping and quoting: a reviewer-based manual check, which means a review queue and a rejection loop rather than an instant retake; and automated assessment of image content (is this actually the damaged car?), which is a machine-learning problem.
