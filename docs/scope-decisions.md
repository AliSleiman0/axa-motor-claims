# Scope decisions

Status: **proposed by developer, not yet acknowledged by client.**
These must be confirmed in writing (scope letter) before code starts.

## In scope — 8 weeks

- **Admin + onboarding** — CRUD for all 4 profile types, invite links by SMS, phone-OTP login, active/inactive, NEXT3 ID mapping
- **Expert module (full)** — claim notification, claim detail view (visa, policy, plate, insured, phone, car make/model, city), "Arrived" button writing date/time/location back to NEXT3, photo capture, voice note, car body damage diagram, the 4 document buckets, quality check with retry, search past claims by visa or plate, expert report upload
- **Garage + Claim Officer survey flow (full)** — new claim declaration, upload, officer notification, visa search in NEXT3, approve/reject with comments, approval rendered as an image into the NEXT3 Survey folder, garage notification, post-repair uploads (discharge, invoice, repair photos)
- **Broker Option 1** — form (insured name, insurance type, address, car value, estimated premium, effective date) + document upload/capture, submit, email routed to the AXA recipient for that insurance type
- **Broker Option 2** — **added 2026-08-19 at the developer's decision.** The broker sends a link to the customer's mobile number; the customer completes the same fields, uploads supporting documents, and captures the four car sides plus roof with side selection and a clarity check; the completed file returns to the broker's profile as *ready to send*; the broker reviews and triggers the email. Builds on Option 1 — same fields, same insurance-type list, same email routing.
- **NEXT3 integration** against client-provided API endpoints

> **Consequence of taking Option 2 in scope, recorded honestly:** it adds an estimated **1.5–2.5 weeks** to an 8-week plan that already covered only ~60–70% of the BRD, and it was the primary negotiating chip — that chip is now spent. It is also the project's largest security surface: a public, unauthenticated page collecting identity documents from members of the public.
>
> **How it was paid for (decided 2026-08-19, see `design.md` §11):** the calendar holds at 8 weeks. **Damage-diagram polish and the second UAT round are dropped**; the rest is absorbed by reusing the expert capture/clarity/upload pipeline for the public flow. **There is no remaining descope lever** — any further slip (late NEXT3 sandbox, InfoSec review on our clock, NEXT3 vendor delay) moves the date day-for-day, and that is said to the client now.

| §6.3's dequeue SQL (quoted verbatim in design.md and HANDOFF §3) | **Two added parameters.** `@now` carries the worker's clock, because the app writes `next_retry_at` from `TimeProvider` and a procedure using `SYSUTCDATETIME()` would compare app time against wall-clock time — the retry schedule would be untestable. `@lease_seconds` reclaims a row whose worker died mid-push; without it the row sits in `processing` for ever, never retried and absent from A2's `failed` list. | Arbitrating a reclaimed outbox row (the lease creates a two-owner window §6.3 never had) | **`attempts` is the concurrency token.** A reclaim increments it, so a stale worker's outcome write carries `AND attempts = <what it claimed>` and matches nothing. Found by the `db-reviewer` pass, not by the tests. *Added 2026-08-20, slice 2.2.* | — |
| A row that repeatedly outlives its worker | **Retired to `failed` by the dequeue itself**, via `@max_attempts`. The give-up rule lives in application code that only runs when a worker survives to record an outcome, so a row that reliably kills its worker would be reclaimed and re-pushed for ever — the lease would have relocated the invisibility it exists to remove rather than fixing it. *Added 2026-08-20, slice 2.2.* | — |
| FIFO draining of the outbox (§6.3's SQL has no ordering either) | **Not implemented, and not a simple oversight.** A CTE with `ORDER BY created_at` makes the sort materialise the candidate set, which locks the rows `READPAST` exists to let a second worker skip; the non-blocking test goes from passing to timing out. Ordering among rows that are all already due matters less than concurrent drain, so it loses. Revisit only with an execution plan in hand — an index supporting the order may allow both. **Consequence to know:** under a backlog an approval PNG can reach NEXT3 after repair photos queued later. *Added 2026-08-20, slice 2.2.* | — |
| Lease expiry depends on the worker's clock, not the database's | **Accepted.** `@now` drives both eligibility and the lease deadline, so a replica whose clock runs more than `LeaseSeconds` fast would reclaim rows nobody abandoned. Single tenant, `minReplicas: 1`, NTP-synced hosts, and — since the concurrency token landed — the worst case is a duplicate push that `clientRef` already dedupes, not a corrupted status. Revisit if §3's worker is ever scaled out. *Added 2026-08-20, slice 2.2.* | — |

| Hand-rolled transactions and Azure SQL connection resiliency | The arrival endpoint runs its explicit transaction inside `Database.CreateExecutionStrategy().ExecuteAsync(...)`, with `ChangeTracker.Clear()` as the first line of the delegate.
