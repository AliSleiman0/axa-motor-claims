# demo-week4.md — the week-4 client demo, beat by beat

**Internal.** Not client-facing. Slice 4.3.
> **Superseded 2026-08-26 by `docs/demo-week6.md`.** This file is kept as the record of what was
> shown at the week-4 payment gate; it predates the broker module, the Option 2 public page, the
> five car shots, the A2 failed-push screen and the Android app, and its rig seeded no broker.
> Use the week-6 script for any demo from now on.
**Audience:** AXA Middle East (HADDAD Ramy + whoever he brings). **Length:** 15 minutes of demo, then questions.
**Milestone:** this demo is the week-4 gate in design.md §11 and triggers the 30% payment.

**Read the two rules before anything else.**

1. **Nothing on screen is client data.** Every visa, plate, name, document-type code and insurance
   type is an obvious placeholder, and beat 5 exists to say so out loud before anybody asks. If a
   value ever looks like something AXA might recognise, that is a bug, not a nice touch.
2. **Follow the beats.** Every improvisation in a demo is a route nobody has walked. The two dry runs
   behind this document walked these routes; they did not walk the others. Every label, button name
   and status word below was read off a real screen, not from the source.

**The gate:** the scope letter and `docs/next3-openapi.yaml` go out **before** this demo (HANDOFF §8).
If they have not gone out, the demo does not happen — the demo is where AXA forms its idea of what
was agreed, and the letter is what stops that idea forming by itself.

## Pre-flight — 15 minutes before, not 2

```powershell
.\scripts\demo-reset.ps1
```

It drops and recreates the database, migrates it, starts Azurite and the API (`Blob__Mode=azure`,
`Push__Mode=webpush`), seeds three users and two assignments **through the admin API**, generates the
demo media, and starts the web app. It takes about 20 seconds and it is idempotent — run it again any
time, including between the two halves of the demo if something goes sideways.

Then, by hand:

| # | Do | Why |
|---|---|---|
| 1 | **Three Chrome profiles**, one per role: **Expert** (window narrowed to phone width), **Garage**, **Officer** (also used for admin in beat 1). **This is load-bearing, not tidiness.** | The session is one bearer token in `localStorage` per origin, so two roles in one profile means signing out and back in mid-demo. Worse: a browser has **one push subscription per profile, not per user**, and the second user to sign in is told *"Notifications are on"* while the server has no subscription for them — they would silently receive nothing. Found in dry run 2; carried as a 7.2 ticket, see `demo-fix-list.md`. One profile per role avoids it entirely. |
| 2 | **Grant the permissions now, in each profile, at `http://localhost:5173`.** Expert: **notifications, location, microphone**. Garage: **notifications**. Officer: none. | All three are Chrome permission bubbles, and a bubble in front of a client is a stall. Location is what **Arrived** asks for; the microphone is the voice note; notifications are beats 2 and 4. The officer needs none — §2 puts them on a desktop and `OfficerLayout` deliberately carries no push panel. |
| 3 | Sign each profile in at `http://localhost:5173/login`. Codes: `.\scripts\demo-otp.ps1 <phone>`. **Set the profiles up first — sign-in is throttled for ~60 s after the reset.** | Four sign-ins is four minutes if you read the log by eye. The reset activates each user by sending them a code, and `Auth:OtpResendSeconds` is 60, so an immediate sign-in gets a 429 and no new code. Doing step 1 and step 2 first spends that minute usefully. |
| 4 | In Expert and Garage, click **Enable notifications** once and check it reports notifications are on. | That click is what registers the `push_subscription` row. Doing it in beat 2 is a permission dialog on a projector. |
| 5 | Second terminal ready; run `.\scripts\demo-outbox.ps1` once now. Editor open on `src\Api\appsettings.Placeholders.json`. | Beats 2–4 read the queue; beat 3 edits that file live. The first run restores a package — `demo-reset.ps1` warms it, but confirm rather than meet a ten-second pause mid-beat. |
| 6 | Confirm `Fake:FailureRate` is `0.0` and `Next3:Mode` is `fake`. | `demo-reset.ps1` warns on the first and refuses on the second. |

**Phones** (all `+999`, an unassigned country code — no real handset can be dialled by accident):

| Role | Phone |
|---|---|
| Admin (seeded by deployment config, §5.4) | `+999000000001` |

## Beat 3 — Kill NEXT3 (3 min) · Expert profile + editor

This is the beat that sells the architecture. Do not rush it — but do watch the clock where marked.

| Do | They see | Say |
|---|---|---|
| In the editor, set `"FailureRate": 1.0` in `src\Api\appsettings.Placeholders.json`. Save. | Nothing. No restart. | "NEXT3 has just gone down. Maintenance window, outage, whichever — this is the simulator's failure switch, and the file reloads live." |
| **Third-party car photos** → `sharp-car-photo.png` → Confirm. Twice. | Both pass the gate and upload exactly as before. | "The expert is standing at a crash site. Notice that nothing on their screen has changed — because nothing about their job depends on NEXT3 being up." |
| `.\scripts\demo-outbox.ps1` | Two rows `pending`, `attempts 1`, a `retry_at` about a minute out, and a `last_error` naming the injected failure. | "The photos are in our storage and queued. The retry schedule is one minute, five, thirty, two hours, six hours — a doomed push takes about twenty-six and a half hours to give up, and then it lands on that admin screen for a human to look at." |
| **Set `"FailureRate": 0.0` and save — within about 40 seconds of that last upload.** | Nothing yet. | "NEXT3 is back." |
| Wait. The worker polls every 30 s and the first retry is ~60 s out, so this takes **up to about 90 seconds**. | — | "Nobody has to do anything. No one re-uploads, no one re-sends an email, no one notices. That is the whole argument — the alternative is a person emailing photos and another person filing them, which is what happens today and is why photos go missing." |
| `.\scripts\demo-outbox.ps1` | Everything `sent`; the recovered rows show `attempts 2` and their error cleared. | "Drained." |

**The 40 seconds matter.** If a row fails a *second* time before you restore, its next retry is **five
minutes** out, not one — that is the schedule doing exactly what it says, but it is longer than a
demo pause. If it happens, do not wait: say *"that one has moved to the five-minute step — you are
watching the backoff work"*, go to beat 4, and show the drained queue at the end of it. Observed in a
dry run; it is a recovery, not a failure.

**Two warnings.** Do not sign anybody in while the failure rate is `1.0` — the fake SMS sender fails
too, so no OTP arrives. And if you open a claim during the outage, E2 shows a stale-claim banner:
that is the design working (serve the cached claim, say so), not a fault. Mention it if it appears;
do not hide it.

## If something goes wrong

| Symptom | Do |
|---|---|
| No notification | Check the permission for `http://localhost:5173` in that profile, and that **Enable notifications** was pressed. `.\scripts\demo-outbox.ps1` shows `push … failed … no active push subscription` when it was not. Then carry on: the same event also lands in the notification log, and both the officer's and the garage's notifications **fall back to email** (§8), which the log shows as `sent`. |
| The queue does not drain | Confirm `FailureRate` is back to `0.0`, then give it another 30 s — the worker polls on that interval. If a row shows `attempts 2`, its next retry is five minutes out; see beat 3. |
| A form does not respond to the first click | Click it again. Seen only under automation during the dry runs, never with a hand on the mouse — noted so it is not mistaken for a bug if it appears. |
| Anything at all | `.\scripts\demo-reset.ps1` — 20 seconds to a clean start. You lose the beats already shown, not the demo. |
| The API log | `demo-artifacts\api.log`. |

## When you are done — stop the rig

```powershell
.\scripts\demo-reset.ps1 -Stop
```

**Do this before going back to writing code.** The demo runs the API with `dotnet run`, so a live
demo holds a lock on `src\Api\bin\Debug\net10.0\Api.exe` and the next `dotnet build` or
`dotnet test` fails with `MSB3027: ... file is locked by "Api"`. It reads like a broken build and is
not one.

Stopping also takes Azurite down, which changes the test counts in a way worth recognising:
`BlobStoreContractTests.TheAzureStore_SatisfiesTheContract` skips when nothing is listening on port
10000, so the suite reads **499 passed / 2 skipped** instead of **500 / 1**. Same suite, same code —
the second skip is the emulator being off, exactly as CLAUDE.md describes. Leave Azurite up
(`-SkipAzurite` on the next reset, or just don't stop it) if you want the Azure half covered.
