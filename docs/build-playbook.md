# build-playbook.md — session-by-session build plan

**What this is:** the ordered list of ~25 build slices for the 8-week plan in `design.md` §11, one slice per Claude Code session, each with its prompt. The spec lives in `design.md`; this file only points at it.
**Status:** written 2026-08-19, before week 1. Weeks 1–2 carry verbatim prompts; weeks 3–8 are outline cards marked *expand when reached*.

---

## How to use it

**The session ritual:**
1. Pick the first unticked slice (they are dependency-ordered — don't skip ahead).
2. Start a Claude Code session in **plan mode** and paste the slice's prompt (prepend the standing preamble below if the session is fresh).
3. Review the plan Claude proposes — check it against the design.md §§ the slice cites — then approve and let it execute.
4. Run the slice's **definition of done**. Green = tick the box, write a one-line learning in *Notes* (what surprised you; the week-upgrade session feeds on these).
5. Review the **test diff** yourself before committing. Claude stops before commit by instruction.

**The drift rule (why prompts look thin):** prompts reference `design.md` §N and never restate its content — no transition tables, no column lists, no config values in this file. When a client answer lands, update `design.md` + the placeholder config; this playbook stays untouched. One source of truth.

**The fidelity rule:** at the start of each week from week 3 on, run one short session: *"Upgrade the week-N cards in build-playbook.md to verbatim prompts, using the Notes from completed slices."* Don't expand weeks early — what week 2 teaches changes how week 6's prompts should read.

**The Friday check:** every Friday, compare ticked slices against the week's row. A week that didn't finish is a **day-for-day slip signal** — per `design.md` §11 there is no descope lever left, so the slip is said to the client immediately, not absorbed silently.

**Slice anatomy:** `☐` status · goal · design.md refs · prompt (or outline) · definition of done (DoD) · test focus · notes.

### ☑ 1.4 The five ports + fakes
**Goal:** every external dependency behind its interface with a working, failure-injectable fake.
**Refs:** design.md §6.2 (interface + fake contract), §3 (senders), §8 (notification log).
**Prompt:**
> Slice 1.4 — create the five ports per design.md §6.2 and §3: `INext3Client` (§6.2 signature verbatim), `IAssignmentSource`, `IEmailSender`, `IPushSender`, `ISmsSender`. Implement fakes for all five: seeded claim data for the NEXT3 fake, config-driven failure injection (`Fake:FailureRate`, `Fake:LatencyMs`), senders logging to the `notification` table (§4). Config selection per §6.2 (`Next3:Mode`, `Next3:AssignmentSource`). No real implementations yet. Register in DI so the arch tests from 1.1 now bind against real namespaces.
**DoD:** app boots fully on fakes; failure injection demonstrably causes retries downstream (assert via a throwaway harness test); arch tests green.
**Test focus:** fake NEXT3 honors `clientRef` dedupe (so outbox tests in 2.2 have a realistic target); notification rows logged per send.
**Notes:** done 2026-08-19 (85 tests, +25). Three things worth carrying forward. (1) **Dedupe order is load-bearing:** the fake checks the `clientRef` sent-log *before* rolling the injected failure, and a *failed* push does not consume the ref. Get that backwards and a transient error either loses the document forever or duplicates it — 2.2's outbox is written against exactly this. (2) **Senders can't hold a DbContext:** they are singletons, `AppDbContext` is scoped, so `NotificationLog` creates its own scope per call and commits its own transaction (unlike `AuditWriter`, which joins the caller's — a send already happened externally and must not vanish on rollback). The plan's `AddDbContextFactory` swap was dropped as unnecessary risk to the 1.2/1.3 suite. (3) **SMS bodies are never logged:** every SMS carries a live credential (OTP code, invite token) that §9 deliberately hashes, so `notification.payload` stays null for SMS — recorded in §4. Also: CA1716 rejects `template` and `to` as interface parameter names (use `templateName`/`recipient`), and `ISmsSender.Send` gaining `templateName` + `recipientUserId` touched OtpService, InviteService and the `CapturingSmsSender` double — that double writes no rows, so send-log tests must use the real fake.

### ☑ 1.5 Option 2 schema + public-surface skeleton
**Goal:** the public surface exists on day one — cheap now, expensive to retrofit.
**Refs:** design.md §4 (`broker_request`, `public_link_token`), §9.1 (token + abuse controls), §3 (public-surface boundary).
**Prompt:**
> Slice 1.5 — create the `broker_request` and `public_link_token` tables per design.md §4 and the `/public/*` endpoint group skeleton per §9.1: token generation (raw shown once, hash stored), the uniform-404 rule for invalid/expired/locked tokens, per-IP and per-token rate limiting middleware, and upload size/count caps from the placeholder config. No UI yet — endpoints + tests only. The §3 boundary holds: this module touches only its own tables and blob prefix; the 1.1 arch test for the public namespace must now bind for real.
**DoD:** token issue→open→lock lifecycle works via API tests; invalid/expired/locked are byte-identical 404s; rate limiter demonstrably throttles; arch test green.
**Test focus:** §9.1 token lifecycle table (reuse-until-locked, expiry, lock-on-submit), enumeration resistance, rate-limit thresholds from config.
**Notes:** done 2026-08-19; reviewed and closed 2026-08-20 (133 tests, +48). Five things worth carrying forward. (1) **Arch rule 2 dictated the module split.** `Api.Modules.PublicSurface` may not reference `Api.Modules.Users`, and `AuthPolicies` lives there — so the public module physically cannot host a `RequireAuthorization` call. B3 therefore sits in a new `Api.Modules.Broker` (which owns `broker_request`), and PublicSurface owns only the token, the endpoints and the limits. A new `Rule2_IsNotVacuous` test now asserts the namespace is non-empty: the rule sat green through 1.1–1.4 purely because there was nothing in it to check. (2) **An endpoint filter is the wrong place for a body-size cap** — minimal-API filters run *after* model binding, so the oversize test failed with 400 (malformed JSON) instead of 413; the whole body had already been read, which is exactly what a cap exists to prevent. It is middleware now, and it also lowers `IHttpMaxRequestBodySizeFeature` so a lying `Content-Length` is cut off by the server. (3) **Rate-limit options must be read per request, not captured at startup**, or they cannot be tested without a second host — `MutableOptionsMonitor` from 1.4 was reused, and since the limiter caches one limiter per partition key, a test that lowers a limit must also use a fresh token *and* a fresh IP. TestServer leaves `RemoteIpAddress` null, so a test-only `IStartupFilter` reads `X-Test-Ip`. (4) **EF defaults a required FK to Cascade** — `broker_request → app_user` came out cascading on the first generated migration and had to be pinned to `Restrict`; the db-reviewer pass caught nothing else. Also: `option` is a reserved SQL keyword, harmless via EF (always bracketed) but it needs `[option]` in any hand-written support query or stored proc. (5) **"Exactly one submission" was not enforced anywhere** — found in the 2026-08-20 review. Submit read `locked_at`, decided, then wrote it; two simultaneous POSTs both passed the read and both returned 200. A `rowversion` on `public_link_token` now makes the database the arbiter, the loser is caught and rendered as the same uniform 404, and its field values and audit row roll back with the batch. The test fires 4 parallel submits and asserts one 200 / three 404s / one audit row; removing the catch turns three of them into 500s, so the race is real rather than theoretical. **The general lesson for 2.2 and 5.2: a read-then-write on a state column is not a state machine — every "this may only happen once" transition needs the guard in the schema.** The 1.5 migration was regenerated (not stacked) since it was still uncommitted; the body-size cap's one-file ceiling is now recorded in scope-decisions as something 5.3/6.1 must raise for multipart.

### ☑ 2.1 Claim cache + assignments
**Goal:** an assignment arrives (from the fake) and an expert sees their claim.
**Refs:** design.md §4 (`claim`, `expert_assignment`), §5.1 (flow + writes), §6.2 (`IAssignmentSource` handler).
**Prompt:**
> Slice 2.1 — implement the assignment path per design.md §5.1 and §6.2: the `claim` cache and `expert_assignment` tables per §4, the single idempotent `AssignmentReceived` handler (dedupe per §6.2), claim-cache refresh rule per §4's `claim` row, and the fake assignment source injecting synthetic assignments on demand. API: expert claim list + claim detail. Push notification via the fake `IPushSender`.
**DoD:** injecting a fake assignment produces the row, the cache fetch, the notification log entry, and it appears in that expert's list only; `dotnet test` green.
**Test focus:** duplicate/replayed assignment is a no-op; stale-cache banner path when the fake NEXT3 is "down"; assignment invisible to other experts.
**Notes:** done 2026-08-20 (167 tests, +34). Four things worth carrying forward. (1) **`IAssignmentSource.Subscribe` hands back no result**, so the demo endpoint could not both use the real delivery path and report an outcome. Split cleanly: the endpoint calls `AssignmentHandler` directly for its typed 200/422, and the tests call `FakeAssignmentSource.Inject` through DI so the startup subscription is what they exercise — same handler either way, which is §6.2's single-funnel guarantee. Resist widening the 1.4 interface for this. (2) **Ordering is the design, not an accident:** the assignment row commits alone, then the cache fetch and the push happen best-effort on top. Both failure paths are tested (`WhenNext3IsDown_TheAssignmentIsStillRecorded`, `WhenThePushFails_...`), because an outage that loses an assignment is the exact bug this project exists to fix. `notified_at` stays null on a failed push — the `notification` row is the record. (3) **`ApiFixture` now swaps `IOptionsMonitor<FakeOptions>` too**, copying the 1.5 `PublicLinkOptions` trick — before this there was no way to make the *booted* app's NEXT3 fail, only a hand-built client. One `FakeBehavior` is shared by NEXT3 and all three senders and the collection is serialized, so `WithNext3Down` restores the old value in a `finally`; forget that and every later test breaks. (4) **The clock is 15 minutes wide.** Two tests failed as 401s, not assertion failures: `Time.Advance(1 hour)` outran `Auth.Jwt.AccessTokenMinutes` with `ClockSkew` zero. Any test travelling further than that must re-login first. Also: `expert_assignment` has **no FK to `claim`** (the cache must stay disposable, or a NEXT3 outage costs assignments), the arrival columns are created now and written in 2.4, and an unmapped `next3_id` is audited and dropped rather than retried — a poller would otherwise loop on data the app cannot fix (#8).

### ☑ 2.2 The outbox
**Goal:** the load-bearing piece, test-first.
**Refs:** design.md §6.3 (everything), §4 (`next3_outbox` — contractual schema).
**Prompt:**
> Slice 2.2 — implement the transactional outbox per design.md §6.3, test-first: the `next3_outbox` table exactly per §4, the one-transaction write helper every producer will use, the `READPAST` dequeue as the sanctioned stored procedure, the worker loop with §6.3's backoff schedule and `failed` terminal state, and `clientRef` idempotency against the fake. Write the failing tests from §6.3's rules first, then implement.
**DoD:** with `Fake:FailureRate` raised, rows visibly retry on schedule and land `sent` or `failed`; atomicity test proves document row + outbox row commit or roll back together; `dotnet test` green.
**Test focus:** atomicity; retry-after-timeout does not duplicate (fake's `clientRef` check); backoff timings; two concurrent workers never double-process (READPAST test).
**Notes:** done 2026-08-20 (197 tests, +34, minus 1.4's throwaway harness which its own comment scheduled for deletion here). Six things worth carrying forward. (1) **§4's `claim_id uniqueidentifier` was unimplementable** — no uniqueidentifier claim id exists anywhere in the model, `claim` is keyed on `visa_no`, and this table must hold no FK to that disposable cache. It is `visa_no nvarchar(50)` now and design.md §4 was *corrected*, not diverged from: the `add-ef-migration` skill and the `db-reviewer` agent both treat outbox drift as a finding, so quiet divergence would have been caught later and cost more. **Read a contractual schema against the model before implementing it, not while generating the migration.** (2) **"No duplicates" does not test READPAST.** Two concurrent `UPDATE TOP (n) … WHERE status='pending'` statements produce disjoint sets with or without the hint — without it the second one simply *blocks* first. The discriminating test holds a transaction open on one connection and gives the second a short command timeout; removing `READPAST` turns it from a pass into a timeout, which was verified by actually removing it. A concurrency test that would pass against the broken version is decoration. (3) **A frozen clock and `SYSUTCDATETIME()` cannot coexist.** `FakeTimeProvider` sits at 2026-08-19 while the database is on real time, so a row whose `next_retry_at` the app wrote was always already due. The procedure takes `@now` from the worker; without it not one backoff timing is testable. (4) **`OutboxWorker` was already registered as a hosted service since 1.4** — turning the shell into a real loop would have had it tick every 30 s against the database the whole serialized collection shares, draining rows other tests were mid-assertion on. Split scheduling (`OutboxWorker`) from behaviour (`OutboxProcessor`), disable the loop with `Outbox__WorkerEnabled=false`, and drive `RunOnce` from tests. The same trap waits for 2.3's cleanup job and the `otp_challenge` purge. (5) **The dequeue claims a batch across the whole table and cannot be scoped to one test's rows** — a batch full of another test's leftovers leaves your row unclaimed and your assertions failing for unrelated reasons. `ClearQueue()` first; safe only because the collection is serialized. (6) **`FromSql` turns every interpolation hole into a parameter**, so the procedure name must be a literal, and nothing may be composed onto the query or EF wraps it in a subquery around `EXEC`. Also: the table must stay trigger-free (`OUTPUT inserted.*`, now asserted against `sys.triggers` rather than only commented), and the full 8-attempt schedule takes **26 h 36 m** — pinned by a test, because it is how long a doomed push takes to reach A2. (7) **The `db-reviewer` pass earned its keep and should run on every migration from here.** It found, and the tests had missed, that **the lease I added introduced a two-owner window**: a reclaimed row is held by both the new worker and the original, and with no arbitrator the slow one wins by arriving last — rewriting a `sent` row to `failed`, or giving a `failed` row a `sent_at`, both of which §7.3's blob deletion and A2's retry list then act on. `attempts` is the concurrency token now (a reclaim increments it, so it *is* the claim's generation counter — no new column, §4 untouched). It also caught that a row which keeps killing its worker would be reclaimed for ever, because the give-up rule sits in code that only runs when a worker survives; the dequeue retires those itself via `@max_attempts`. **A feature that fixes one hole often digs another one next to it — audit the fix, not just the original design.** (8) **FIFO draining and READPAST are in tension.** A CTE with `ORDER BY created_at` makes the sort materialise the candidate set and lock exactly the rows READPAST exists to skip; the non-blocking test went red. Ordering lost. The same bite recurred in miniature when the new abandon statement was written without the hints — one unhinted `UPDATE` anywhere in the procedure makes the whole thing blocking. **Every statement in that proc needs `WITH (UPDLOCK, READPAST, ROWLOCK)`, not just the claim.** (9) **`IsConcurrencyToken()` is invisible to `has-pending-model-changes`** — it reports "no changes" while the snapshot genuinely lacks it, because the annotation emits no DDL. The migration had to be regenerated (safe, still uncommitted) to get it into the snapshot; check the snapshot by eye after adding a token.

### ☑ 2.3 Media pipeline — server side
**Goal:** a file becomes a `document` row + blob + outbox push, with the lifecycle rules enforced structurally.
**Refs:** design.md §7 (all), §4 (`document`).
**Prompt:**
> Slice 2.3 — implement the server media pipeline per design.md §7: the `document` table per §4, a **streamed** multipart upload endpoint (no buffering into memory — §7.3's failure order: blob PUT first, then the one-transaction rows via 2.2's helper), bucket rules per §7.1 with the `origin` flag, server-side re-validation per §7.2 item 5, and the cleanup job whose delete query structurally joins on outbox `sent` per §7.3. Use Azurite (Docker) or the Blob emulator for local dev — document the choice in CLAUDE.md's commands section.
**DoD:** upload→document row→outbox row→fake push→`sent`→cleanup-eligible, verified by test; a `failed` push's blob survives cleanup; `dotnet test` green.
**Test focus:** §7.3 lifecycle rules (especially never-delete-before-sent), capture-only bucket rejection, oversize/wrong-type rejection.
**Notes:** done 2026-08-20 (263 tests, +66). Eight things worth carrying forward. (1) **A stray `AsNoTracking()` in a composed subquery silently disarmed the retention sweep.** `OutboxSentQuery` projected to a `Guid` and looked free to mark no-tracking; EF applies the tracking behaviour of the *combined* expression tree, so the outer `Documents` query came back untracked, `blob_deleted_at` was never written, and `SaveChanges` reported success having done nothing. The blob was deleted, the row still said it was held, and the same rows were re-swept on every pass. Two tests passed either way — only the one asserting the *flag* caught it. **When you compose an IQueryable from another class, tracking is part of what you inherited.** (2) **Architecture rule 4 made `OutboxWriter` uncallable and nobody noticed**, because 2.2 shipped with no producers: a called method's return type is part of the calling type's IL, so returning `Next3OutboxMessage` put every future producer in violation. It returns `Guid` now. **A boundary rule with nothing on the other side of it is untested — the first real consumer is the test.** (3) **The `db-reviewer` pass again found what the tests missed, and the worst finding was in my fix, not the design** — the retention sweep deleted up to 500 blobs and committed once, so one undeletable blob discarded the `blob_deleted_at` and audit rows already staged *for bytes that were physically gone*, and the deterministic batch then stalled retention behind it for ever. Also: the unique index on `outbox_message_id` is a safety property (one confirmed push must license exactly one deletion), the `queued ⇔ outbox row exists` check constraint, a missing `blob_key` index, `ValueGeneratedNever`, and a doc-type lookup sitting *after* the blob PUT so a config typo leaked a blob per upload. (4) **`Down()` on this table is destructive beyond it**: drop `document` and 24 hours later the orphan sweep deletes every blob in the container, including bytes named by `pending`/`failed` outbox rows — warning written into the migration, where someone will be standing when it matters. (5) **No image library.** ~90 lines of JPEG SOFn / PNG IHDR parsing beats a licence question at handover (ImageSharp v3's split licence) and a Windows-only API (`System.Drawing`); it doubles as the magic-byte check. A 128 KB bounded peek is needed because phone EXIF pushes the frame header tens of kB in — and `unreadable_image` must stay distinct from `content_type_mismatch`, or the answer points at an attacker who is not there. (6) **Streaming costs an ordering contract:** metadata parts must precede the file part, because a bucket learned after the bytes reached storage cannot apply §7.1's capture-only rule. Refused with a named code rather than silently buffered. (7) **Azurite lags the SDK**: Azure.Storage.Blobs 12.29 sends API version 2026-06-06, Azurite 3.36 rejects it, so `--skipApiVersionCheck` is mandatory and is in CLAUDE.md. The npm package is `azurite` with a binary named `azurite-blob` (`npx -p azurite azurite-blob`), which matters when Docker Desktop is not running. (8) **A contract test that only feeds a `MemoryStream` proves less than it looks**: the upload path hands the store a non-seekable, unknown-length stream, so the contract test now builds the same `PrefixedStream`+`LimitedStream` composition. A skippable `[AzuriteFact]` keeps `dotnet test` Docker-free while still exercising the real adapter when the emulator is up — the shape 3.3 wants for fake-vs-sandbox.

### ☑ 2.4 Expert screens E1/E2 + Arrived
**Goal:** the expert's daily flow in the browser.
**Refs:** design.md §5.1 (E1/E2 rows), §2 (screen gating).
**Prompt:**
> Slice 2.4 — build E1 (claim list, newest-first with media counts) and E2 (claim detail with the Arrived button) per design.md §5.1: Arrived writes per its table row (timestamps + coordinates + outbox `update_arrival`), disabled after first press, blocking explanation on geolocation denial, and Arrived does NOT gate capture (§5.1's recorded interpretation). TanStack Query for server state; logic in hooks, components render.
**DoD:** full flow works in the browser against the fake; Arrived visible in outbox as `sent`; `npm run build` + tests green.
**Test focus:** Arrived idempotence (double-press), geolocation-denied path, list scoped to the logged-in expert.
**Notes:** done 2026-08-20 (283 xUnit +20, and a new web suite of 20). **No migration and almost no new server code** — 2.1 created the arrival columns and 2.2 created `EnqueueArrival`, so the slice was one endpoint plus the whole web layer. Seven things worth carrying forward. (1) **"Idempotent" needed the guard in the WHERE clause, not in an `if`.** The sequential double-press that the DoD names is the easy half; four simultaneous presses all pass a read-then-write check, and the damage is real — two `arrived_at` values and two `update_arrival` pushes tell NEXT3 the expert arrived twice at two different times. `WHERE arrived_at IS NULL` on an `ExecuteUpdate` settles it; removing the clause was verified to turn the concurrency test from 1 arrival into 4. This is the third slice in a row where 1.5's lesson was the load-bearing one. (2) **`ExecuteUpdate` costs an explicit transaction.** It runs its own statement immediately, outside `SaveChanges`, so without `BeginTransactionAsync` the outbox row would commit separately from the row that caused it — §4's one-transaction rule broken by the first endpoint that actually depends on it. Only place in the codebase with an explicit transaction; commented as such. (3) **A concurrency token on `ArrivedAt` was the wrong tool**, though it is the 1.5/2.2 idiom: EF applies a token to *every* write of the entity, so a concurrent E2 first-open would fail its `opened_at` save with `DbUpdateConcurrencyException`. A guard that belongs to one transition should not be pinned to the whole row. (4) **The double-press latch cannot be `mutation.isPending`.** Two taps in the same tick both run before React re-renders, so `isPending` is still false for the second — swapping the `useRef` latch for `isPending` was verified to turn one request into two. Same class of bug as (1), one layer up. (5) **Timestamps arrive without a `Z`.** A value the server just computed serialises as UTC; the same value read back out of SQL is `DateTimeKind.Unspecified` and comes through bare, which the browser reads as local — a four-hour error in GST on the one screen whose job is recording when the expert arrived. Normalised in the web layer (`toUtcDate`), not by reconfiguring EF/JSON, which would have put the 282 exact-timestamp assertions at risk. (6) **Vitest without `globals` means `@testing-library`'s auto-cleanup never registers** — it looks for a global `afterEach`. Three page tests failed with "found multiple elements" before `src/testing/setup.ts` existed; every render had been stacking into the same document. (7) **`@(...)` around a PowerShell pipeline result**: a single matching line is a *string*, and `[-1]` on a string is its last character, so the manual-pass script read an OTP of "6". (8) **The `db-reviewer` pass found the worst bug in the slice, and the tests had pinned it.** `ArrivalInfo` carried `DateOnly` + `TimeOnly` — a faithful reading of §6.1, written in 1.4 when nothing filled it. The moment 2.4 filled it from a UTC instant, the offset was thrown away *at capture*: an expert arriving at 01:30 GST would be pushed to NEXT3 as arriving the previous calendar day, on the one field a claims dispute turns on, in a row that is durable for up to 26 hours and cannot be repaired from its own payload. It is a `DateTimeOffset` now, with the split moved to `RealNext3Client` and a new `Next3:ArrivalTimeZone` placeholder (#6, design.md updated).
