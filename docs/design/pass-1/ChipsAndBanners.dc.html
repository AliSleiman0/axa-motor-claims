An outage is a normal condition in this product, not an exception screen: NEXT3 has maintenance windows and the field user is on a roadside connection. The banners below are built so the app can say what is wrong without ever taking work away from the person holding the phone.

StatusChip

Labels are the shipped strings — a garage never sees the word “rejected”.

Colour carries meaning, never decoration: grey is not started, amber is with someone else, green is agreed, red is finished badly, blue is work in progress, dark is finished well. Every chip pairs a tint, a border and a text colour, so it survives a greyscale print and a colour-blind reader.

AlertBanner  vs  StatusBanner

role="alert" · role="status"

The difference has to be visible at arm's length: an AlertBanner is filled and bordered on its intent colour and it means something did not happen. A StatusBanner is a quiet strip on a neutral tint and it means the app is telling you where things stand. Both carry an icon and a whole sentence — never a code, never “an error occurred”.

AlertBanner / blocking Arrival was not sent. AXA records where the expert arrived, so this app cannot report an arrival without a location. Allow location access for this site and press Arrived again.
AlertBanner / outage NEXT3 is unreachable. Showing the copy last fetched on 20 Aug 2026, 09:30. Phone form, where the width is not there: NEXT3 unreachable — showing last known details.
StatusBanner / informational This declaration is with a claim officer. You will get a notification on this device when it has been reviewed.
StatusBanner / queue 3 photos are queued for AXA. They stay on this device and go automatically — keep working. Proposed copy; there is no such banner in the build yet. Nothing here blocks capture: an upload that cannot reach NEXT3 still succeeds locally, which is the whole point of the queue behind it.

PushIndicator

Used on DocumentRow · three states, one line each

Deliberately quiet — grey text and a 16 px glyph, not a chip. A document's delivery is reassurance, not a status the user has to act on; the only one that ever needs attention is a failure, and failures are the admin's failed-push queue, not the field user's problem.

Only the third of these exists in the build today; the first two are new surface over a value the API already returns. The third state is also the one that must never render as a broken thumbnail — the bytes are genuinely gone, so the row shows the file name and no preview.
